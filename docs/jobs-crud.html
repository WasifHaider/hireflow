Jobs CRUD

HireFlow backend — tenant-scoped job postings with JWT protection, soft delete, pagination, and filters. NestJS + Prisma + Supabase PostgreSQL.

Overview

After recruiter authentication (company signup, sign-in, GET /auth/me), Jobs CRUD is the next foundational piece. Every endpoint lives under /jobs, requires a valid JWT (JwtAuthGuard), and scopes all data to the authenticated user's companyId from the token.

Base URL (dev): http://localhost:3200  |  Swagger: http://localhost:3200/api/docs

API Endpoints

Method Path Purpose
POST /jobs Create a job under the current user's company
GET /jobs List company jobs (pagination, filters, search)
GET /jobs/:id Get one job (tenant-scoped)
PATCH /jobs/:id Partial update (tenant-scoped)
DELETE /jobs/:id Soft delete — sets deletedAt, returns 200 + body

Tenant Isolation

Never trust the client for companyId. It is never accepted in create/update DTOs. It always comes from the JWT via @CurrentUser() → user.companyId.

Every service method receives companyId as a parameter derived from the authenticated user, never from request body or query.

404 vs 403

When Company B's token tries to access Company A's job by UUID, the API returns 404 Not Found — not 403 Forbidden. The query is: 

findFirst({ where: { id, companyId, deletedAt: null } })

If the job exists but belongs to another tenant, no row matches → same response as a non-existent ID. This avoids leaking whether a UUID exists in the system.

Do not use findUnique({ where: { id } }) for tenant reads — that loads any job by ID regardless of company.

What happens if you forget companyId?

A cross-tenant data leak: any authenticated user could read or mutate another company's jobs by guessing UUIDs. This is catastrophic in production — always include companyId in the where clause.

Architecture

Client (Swagger / frontend) │ Authorization: Bearer <JWT> ▼ JobsController @UseGuards(JwtAuthGuard) │ @CurrentUser() → SafeUser (id, companyId, …) ▼ JobsService companyId from user, never from DTO ▼ PrismaService Job queries always filter companyId + deletedAt: null ▼ Supabase PostgreSQL jobs table (snake_case columns)

Unsupported("vector(1536)")

Prisma does not natively model pgvector columns. Unsupported tells Prisma to include the column in SQL migrations but not expose it on the generated client for normal CRUD. The migration runs CREATE EXTENSION IF NOT EXISTS vector and creates job_embedding vector(1536). Stays NULL until embedding generation is built.

Relations

  • Company.jobs — one-to-many
  • User.createdJobs — @relation("UserCreatedJobs") named for future User→Job relations (e.g. assignments)
  • onDelete: Cascade on company; Restrict on creator

Indexes

  • @@index([companyId])
  • @@index([companyId, deletedAt]) — speeds up WHERE company_id = ? AND deleted_at IS NULL (the default list query)

2DTOs

Location: apps/backend/src/jobs/dto/

create-job.dto.ts

  • title — 2–200 chars
  • description — min 20 chars
  • requirements — min 10 chars
  • location — 2–100 chars
  • jobType, employmentType — @IsEnum from Prisma
  • salaryMin / salaryMax — optional ints ≥ 0; SalaryRangeConstraint ensures max ≥ min when both set
  • salaryCurrency — optional 3-letter ISO (@Matches(/^[A-Z]{3}$/))
  • status — optional; service defaults to DRAFT
  • No companyId — rejected by forbidNonWhitelisted: true

update-job.dto.ts

export class UpdateJobDto extends PartialType(CreateJobDto) {}

PartialType from @nestjs/mapped-types makes every create field optional and copies validation decorators. PATCH can send only changed fields. One source of truth for validation rules.

list-jobs-query.dto.ts

Separate DTO because query params are not JSON bodies.

HTTP query strings are always strings (?page=2 → "2"). @Transform + ValidationPipe({ transform: true }) coerces to numbers before @IsInt() runs.

3JobsService

apps/backend/src/jobs/jobs.service.ts

create(dto, user)

  • Sets companyId: user.companyId, createdById: user.id
  • status defaults to DRAFT if omitted
  • If status is PUBLISHED → publishedAt: new Date()
  • salaryCurrency defaults to USD in service if omitted

findAll(query, companyId)

where: { companyId, deletedAt: null, …filters }
orderBy: { [sortBy]: sortOrder }
skip / take for pagination
$transaction([ findMany, count ])  // parallel

Returns:

{ data, total, page, pageSize, totalPages }

Search uses Prisma OR with contains + mode: 'insensitive' on title and location.

findOne(id, companyId)

findFirst({ where: { id, companyId, deletedAt: null } })
→ NotFoundException('Job not found') if missing

update(id, dto, companyId)

  • Calls findOne first (ownership check)
  • If dto.status === PUBLISHED and existing publishedAt is null → set publishedAt: new Date()

softDelete(id, companyId)

  • Calls findOne first
  • Sets deletedAt: new Date()
  • Returns { id, deletedAt }

4JobsController

apps/backend/src/jobs/jobs.controller.ts

  • @Controller('jobs')
  • @UseGuards(JwtAuthGuard) at class level — all routes protected
  • @ApiTags('Jobs'), @ApiBearerAuth()
  • ParseUUIDPipe on :id — rejects malformed IDs with 400 before hitting the DB
  • DELETE uses @HttpCode(200) because the response body includes { id, deletedAt } (not 204 No Content)
POST /jobs @CurrentUser + CreateJobDto GET /jobs @CurrentUser + ListJobsQueryDto GET /jobs/:id ParseUUIDPipe + @CurrentUser PATCH /jobs/:id ParseUUIDPipe + UpdateJobDto + @CurrentUser DELETE /jobs/:id ParseUUIDPipe + @CurrentUser → 200 + { id, deletedAt }

6Manual End-to-End Testing (Swagger)

  1. Start server: cd apps/backend && npm run dev
  2. Open http://localhost:3200/api/docs
  3. Sign up Company A — POST /auth/company/signup 
    {
  "companyName": "Acme Corp",
  "fullName": "Alice Admin",
  "email": "alice@acme-test.com",
  "password": "SecurePass1"
}
    Save accessToken as Token-A.
  4. Sign up Company B — different email (e.g. bob@beta-test.com). Save token as Token-B.
  5. Authorize with Token-A. Create 3 jobs via POST /jobs: 
    {
  "title": "Senior Backend Engineer",
  "description": "Build scalable APIs with NestJS and PostgreSQL for our hiring platform.",
  "requirements": "- 5+ years Node.js\n- PostgreSQL\n- REST API design",
  "location": "Remote",
  "jobType": "REMOTE",
  "employmentType": "FULL_TIME",
  "salaryMin": 120000,
  "salaryMax": 180000,
  "status": "PUBLISHED"
}
    Vary titles/status: one DRAFT, two PUBLISHED (e.g. Product Designer, Data Scientist).
  6. GET /jobs — expect 3 jobs, paginated wrapper with data, total, etc.
  7. GET /jobs/{id} — copy an ID from the list; expect 200 + job JSON.
  8. PATCH /jobs/{id} — e.g. { "title": "Staff Backend Engineer" } — verify update.

Critical tenant isolation test

  1. Swagger Authorize → paste Token-B.
  2. GET /jobs → expect zero jobs (empty data).
  3. GET /jobs/{company-a-job-uuid} → expect 404 Not Found (not 403, not 200 with leaked data).
  4. PATCH and DELETE on Company A's job ID → expect 404 each.

Soft delete test (Token-A)

  1. DELETE /jobs/{id} on your own job → 200 with { "id": "...", "deletedAt": "..." }.
  2. GET /jobs → deleted job no longer in list.
  3. GET /jobs/{deleted-id} → 404.
  4. Supabase Studio → jobs table → row still exists with deleted_at populated (data retained, hidden from API).
If any isolation test returns 200 for another tenant's job, stop and fix before shipping — that is a production data leak.

Out of Scope (v1)

Intentionally not implemented in this phase:
  • File upload (resumes, logos)
  • Embedding generation (jobEmbedding stays null)
  • Candidate / Application models
  • Background jobs / queues
  • Per-endpoint rate limiting
  • Role-based guards beyond JWT
  • Caching
  • Frontend changes
