Recruiter Authentication

HireFlow backend — custom JWT auth for company signup, sign-in, and protected routes. NestJS + TypeScript + Prisma + Passport.

Overview

We built a self-hosted JWT authentication system for recruiters (v1). It does not use Supabase Auth — passwords are hashed with bcrypt, tokens are signed with JWT_SECRET, and protected routes validate the Bearer token on every request.

Three working endpoints:

Method Path Purpose
POST /auth/company/signup Create Company + first admin User, return JWT
POST /auth/signin Authenticate by email/password, return JWT
GET /auth/me Protected — return current user (proves JWT guard)

Base URL (dev): http://localhost:3200  |  Swagger: http://localhost:3200/api/docs

Request / Response Shape

Signup & Sign-in success

{
  "user": { "id", "companyId", "email", "fullName", "role", "avatarUrl", "lastLoginAt", ... },
  "company": { "id", "name", "slug", "industry", "size", ... },
  "accessToken": "<JWT string>"
}
Never return passwordHash in any response. It is stripped in AuthService and in JwtStrategy.validate().

Architecture

┌─────────────┐ POST /auth/company/signup │ Client │ POST /auth/signin │ (Swagger) │ GET /auth/me + Authorization: Bearer <token> └──────┬──────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ ValidationPipe (global) — DTOs, whitelist, transform │ └──────────────────────────────┬───────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ AuthController │ └──────────────────────────────┬───────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ AuthService — bcrypt, Prisma, JwtService.sign() │ └──────────────────────────────┬───────────────────────────────┘ signup/signin │ GET /auth/me creates/updates DB │ │ returns accessToken │ ▼ │ ┌────────────────────────────┐ │ │ JwtAuthGuard → Passport │ │ │ JwtStrategy │ │ │ • extract Bearer token │ │ │ • verify signature + exp │ │ │ • validate(payload) │ │ │ → re-fetch user from DB │ │ │ • attach to req.user │ │ └─────────────┬──────────────┘ │ ▼ │ @CurrentUser() → controller ▼ ┌─────────────────────┐ │ PostgreSQL │ │ (Supabase) │ │ companies, users │ └─────────────────────┘

Passport concepts

  • PassportModule — integrates Passport with Nest.
  • Strategy (jwt) — defines how to extract and verify the JWT, then what to put on req.user.
  • Guard (AuthGuard('jwt')) — runs the strategy before the route handler; blocks with 401 if invalid.

1DTOs

SignupCompanyDto and SigninDto use class-validator + class-transformer. The global ValidationPipe rejects invalid bodies with 400 before business logic runs.

Field (signup) Rules
companyName Required, 2–100 chars
slug Optional; ^[a-z0-9-]+$, 2–50 chars
fullName Required, 2–100 chars
email Valid email; trimmed + lowercased via @Transform
password Min 8 chars; at least one letter and one number
industry Optional string
size Optional: 1-10 | 11-50 | … | 500+
Why lowercase email? Email is case-insensitive for identity. Normalizing at the DTO boundary keeps the unique index stable and avoids duplicate accounts (Jane@x.com vs jane@x.com).

Properties use email!: string — the ! definite assignment assertion satisfies strictPropertyInitialization; Nest fills fields from JSON at runtime, not via a constructor.

2JWT Payload Type

interface JwtPayload {
  sub: string;       // user ID (JWT standard "subject")
  companyId: string;
  email: string;
  role: 'ADMIN' | 'RECRUITER';
}
  • sub — standard JWT claim for the principal (user id). Libraries expect this name.
  • Minimal payload — JWTs are only signed, not encrypted; anyone with the token can read claims. Full user state is loaded from the DB in the strategy.

3AuthService

signupCompany(dto)

  1. Check email uniqueness (409 if taken).
  2. Hash password with bcrypt outside the transaction (slow; don’t hold DB locks during hashing).
  3. Generate slug from companyName if omitted (slugify).
  4. Resolve unique slug (append random 4-char suffix if collision).
  5. prisma.$transaction — create Company, then User with role: ADMIN, set lastLoginAt.
  6. On P2002 slug race — retry with new slug (up to 3 attempts).
  7. generateToken(user) → return user (no hash), company, token.

signin(dto)

  1. Find user by email (include company).
  2. If missing user or bcrypt.compare fails → UnauthorizedException('Invalid credentials') — same message for both (prevents email enumeration).
  3. Update lastLoginAt, sign JWT, return safe user + company + token.

generateToken(user) (private)

Builds JwtPayload and calls jwtService.sign(payload).

4JwtStrategy

Extends PassportStrategy(Strategy) from passport-jwt:

  • Extracts token from Authorization: Bearer <token>
  • secretOrKey from JWT_SECRET
  • ignoreExpiration: false
  • validate(payload) — findUnique user by payload.sub; 401 if deleted; returns user without passwordHash → becomes req.user
Why re-fetch from DB? A token may outlive the user (account deleted after issue). One indexed lookup per request keeps req.user trustworthy.

5JwtAuthGuard

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {}

Thin wrapper around Passport’s JWT guard. Same behavior today; allows custom 401 handling or public-route metadata later without changing every controller.

6CurrentUser Decorator

getMe(@CurrentUser() user: SafeUser): SafeUser

createParamDecorator reads request.user set by the strategy. Cleaner than @Req() req in every handler. SafeUser is imported with import type for emitDecoratorMetadata + isolatedModules.

7AuthController

@Controller('auth') — all routes prefixed with /auth.

  • Swagger: @ApiTags('auth'), @ApiOperation, @ApiResponse
  • GET /auth/me — @UseGuards(JwtAuthGuard), @ApiBearerAuth()

8AuthModule

  • JwtModule.registerAsync — JWT_SECRET, JWT_EXPIRES_IN from ConfigService
  • PassportModule
  • Providers: AuthService, JwtStrategy, JwtAuthGuard
  • Exports: AuthService, JwtAuthGuard (for other modules)

AppModule imports ConfigModule.forRoot({ isGlobal: true }), PrismaModule, AuthModule.

9Swagger Bearer Auth

In main.ts:

.addBearerAuth({
  type: 'http',
  scheme: 'bearer',
  bearerFormat: 'JWT',
})

Swagger UI shows an Authorize button — paste the accessToken from signup/signin to call GET /auth/me.

10Manual End-to-End Testing

  1. Start server: cd apps/backend && npm run dev
    Expect: Nest application successfully started and routes mapped (server stays idle — that is normal).
  2. Open http://localhost:3200/api/docs
  3. POST /auth/company/signup — example body: 
    {
  "companyName": "Acme Recruiting",
  "fullName": "Jane Doe",
  "email": "jane@acme.com",
  "password": "SecurePass1",
  "industry": "Technology",
  "size": "11-50"
}
    Verify: user, company, accessToken; no passwordHash.
  4. Supabase Studio — one row in companies, one in users; password_hash starts with $2b$10$.
  5. POST /auth/signin — same credentials → new token, same shape.
  6. Wrong password → 401 with "Invalid credentials" (generic message).
  7. Click Authorize → paste token (no Bearer prefix).
  8. GET /auth/me → current user JSON.
  9. Remove auth → GET /auth/me → 401.

Out of Scope (v1)

Intentionally not implemented in this phase:
  • Supabase Auth integration
  • Refresh tokens (single access token, 7d expiry)
  • Email verification, password reset, 2FA
  • Google / LinkedIn OAuth
  • Candidate auth
  • Role-based guards beyond JWT (@Roles('ADMIN'))
  • Rate limiting on auth endpoints
  • Frontend changes
