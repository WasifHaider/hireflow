Sub-phase D · Backend

Candidate Auth + Email Verification + Reconciliation

A second, separate JWT auth flow for job applicants — signup, email verification, signin — with implicit linking of anonymous applications via the defense-2 model.

Why this change

HireFlow already has recruiter auth (JWT, users table). Candidates currently apply anonymously — a candidates row is upserted by email in public.service.ts. This phase gives candidates real accounts so they can sign in and track applications across companies, while keeping security tight:

  • Defense-2 reconciliation — anonymous applications link to an account only after email verification, never at signup. The candidate row is the anonymous row, so linking is implicit.
  • Type-based authz — one JWT system, two user types. The token carries userType; specialized guards stop a candidate token from reaching recruiter endpoints (and vice-versa).
  • Verification gate — JWT issued only after verifying email; signin blocked until verified.

Build steps

1 Prisma migration — Candidate auth fields

Add to the existing Candidate model. All nullable, because a row may exist purely as an anonymous applicant.

passwordHash                    String?    // null = anonymous applicant
emailVerifiedAt                 DateTime?  // null until verified
emailVerificationToken          String? @unique
emailVerificationTokenExpiresAt DateTime?
lastLoginAt                     DateTime?
// authUserId String? @unique — already present, reserved for future
ColumnWhy nullable
passwordHashAnonymous applicants have no password. Set on signup.
emailVerifiedAtNull until the verification link is clicked — the gate for signin + reconciliation.
emailVerificationTokenOnly set between signup and verification; cleared after. Unique = single-use lookup key.
emailVerificationTokenExpiresAt24h window; null when no pending verification.
lastLoginAtNull until first successful auth.
Destructive: npx prisma migrate dev --name add-candidate-auth-fields — confirm before running.

2 JWT payload → discriminated union

Replace the flat JwtPayload with a union keyed on userType. Recruiter tokens add companyId + role; candidate tokens carry only sub, email, userType. Recruiter generateToken() stamps userType: 'recruiter'. Legacy tokens (no userType) are treated as recruiter for backward compatibility.

3 MailService — Resend + console fallback

New global MailModule. If RESEND_API_KEY is set, send via Resend; otherwise log a clearly-framed block (URL visible) to the backend logs. sendVerificationEmail() catches and logs errors, never throws — a mail failure must not block signup. The template ships both HTML (indigo CTA, 24h expiry note, plain-link fallback) and plain text.

4 Split guards + branch the strategy

The strategy fetches the right table by userType (candidates must have emailVerifiedAt set or it's a 401). Two guards extend the base:

  • RecruiterAuthGuard → requires userType === 'recruiter', else 401 "Recruiter access required"
  • CandidateAuthGuard → requires userType === 'candidate', else 401 "Candidate access required"
Critical swap: every existing protected endpoint (jobs, applications, /auth/me) moves from JwtAuthGuard → RecruiterAuthGuard so candidate tokens can't reach them.

5 Candidate auth module

EndpointBehaviour
POST /auth/candidate/signupUpsert by email; set passwordHash + token (never emailVerifiedAt). Send email. 201, no JWT. Throttle 5/min.
GET /auth/candidate/verify?token=Set emailVerifiedAt, clear token (in a transaction). Issue candidate JWT. Reconciliation is implicit here.
POST /auth/candidate/signin401 invalid creds · 403 if unverified · else JWT. Throttle 5/min.

Token = crypto.randomBytes(32).toString('hex') — a cryptographically random opaque string, not a JWT: single-use, server-revocable (we delete it), and leaks no payload.

6 Candidate dashboard endpoint

GET /candidate/me/applications — guarded by CandidateAuthGuard. Returns all applications for the candidate (newest first) with nested job + company. Applications to soft-deleted jobs are shown with a jobAvailable: false flag rather than hidden, so the candidate keeps a record of every application they submitted.

Reconciliation flow (defense-2)

anonymous apply  →  candidate row {passwordHash:null, emailVerifiedAt:null}  + application
candidate signup →  SAME row gains passwordHash + token   (emailVerifiedAt STILL null)
verify email     →  emailVerifiedAt set, token cleared     →  application now visible
                    (no extra linking — apps always pointed at this row)

Verification checklist

  • ✓ Signup → 201, no JWT; DB token set, emailVerifiedAt null; email delivered/logged
  • ✓ Signin pre-verify → 403
  • ✓ Verify → 200 + JWT; emailVerifiedAt set, token null
  • ✓ Signin post-verify → 200; JWT has userType:'candidate', no companyId
  • ✓ Reconciliation: anonymous app appears after verify + signin
  • ✓ Cross-type: candidate→/jobs 401, recruiter→/candidate/me/applications 401
  • ✓ Bad/expired token → 400 · duplicate verified signup → 409 · 6th signup → 429
